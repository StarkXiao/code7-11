# 设计说明

## 1. 目标与范围

冷链温控追溯系统要回答四类问题：

1. **现在有没有超温？** —— 传感器读数实时判定，越限立刻报警（SSE 推送）。
2. **是谁的责任？** —— 把超温时长落到具体承运环节/责任方，跨交接时多方分摊。
3. **这批货经历了什么？** —— 按批次给出环节链、温度、事件、报警融合的完整时间线。
4. **结论可不可信？** —— 所有状态由追加事件重放得到，任何时候都能回到原始记录复核。

本期不包含：多用户权限、前端大屏、告警通知渠道（短信/钉钉）、温度预测。
SSE 已提供实时出口，通知渠道可作为订阅者直接扩展。

## 2. 分层

```
simulator（车载模拟器）
   │  sensor_code + temp + ts（HTTP 或进程内）
   ▼
api.js ── HTTP / SSE（node:http，无框架）
   ▼
service.js ── 领域状态机：建档、交接、读数入库、报警生命周期、回溯组装
   ▼
engine.js ── 纯函数规则：越限判定 / 级别 / 环节定位 / 责任拆分（无 IO，易测试）
   ▼
store.js ── append-only JSONL 事件日志 + 重放
```

engine.js 不碰存储与时钟，所有时间以参数传入，因此可以用固定时间做确定性测试。

## 3. 事件溯源

不做就地更新，状态变更全部追加事件：

| 事件 | 含义 |
|---|---|
| `shipment.created` | 批次建档（温区随批次固化） |
| `vehicle.registered` / `sensor.registered` | 载具、车载传感器 |
| `segment.started` / `segment.ended` | 承运环节开始 / 交接结束 |
| `event.recorded` | 开门、设备故障、交接备注 |
| `reading.ingested` | 读数入库（含 `orphan` 标记） |
| `alarm.opened` | 报警产生 |
| `alarm.closed` / `alarm.closed_resolved` | 报警闭环 / 闭环时的责任拆分快照 |

启动时顺序重放重建内存状态。新增事件通过订阅者同步推进内存，因此运行期查询无需重读文件。

闭环时把责任拆分成一份快照（`alarm.closed_resolved`）是刻意的：
报警时长依赖"当时读到了哪些读数"，重放历史批次时不能用今天的时钟去延伸开放区间。

写入顺序对重放正确性很重要：首条越限读数先写 `alarm.opened` 再写
`reading.ingested`，这样重放到读数时报警已存在，可以正确挂接 `alarm_id`。

## 4. 读数如何找到责任环节

读数只带 `sensor_code`，由传感器解析出 `(载具, 车厢)`，再用读数时刻定位环节：

1. 在该**车厢**的环节链里，找到时刻 `ts` 所属的虚拟承运区间（最后一个 `started_at ≤ ts` 的环节）；
2. 该环节的载具必须与上报传感器的载具一致，否则读数为**孤儿**。

虚拟承运区间：`[本环节开始, 下一环节开始)`。由此自然得到两条行业惯例：

- **交接空档归上家**：上家已结束、下家还没开始的时间，仍算上家在承运；
- **换车即断链**：下家环节开始后，旧车传感器再来的读数无承运关系，记为孤儿。

月台、医院收货温控位以 `kind=dock` 的载具建模并安装传感器，
使"车→月台→车→收货位"的温度链全程连续，交接点不丢数据。

## 5. 报警生命周期

报警键为 `(批次, 车厢)`，与具体传感器/载具解耦：

```
读数在限区间内
  └─ 有 open 报警？→ 闭环（close）
读数越限
  └─ 有 open 报警？→ 追加越限读数（excursion）
                   └─ 没有 → 新报警（alarm_opened）
```

因此报警跨越干线车与月台车时仍是**同一个报警**，闭环后一次性算出多方责任，
而不是产生两个互不相干的报警。

级别在报警开启时为 `trivial`，随读数增加按当前最大偏离与累计时长动态升级，
闭环时固化。方向（high/low）决定用上限还是下限算偏离。

## 6. 责任拆分的时间账

采样值按阶跃函数解释：读数 r_i 代表 `[ts_i, ts_{i+1})` 的温度。
选择阶跃而不是"上一条→这一条"的回看口径，是因为交接瞬间两台设备可能各有一条
同一时刻的读数：回看口径会在两台设备间产生零宽/错分；阶跃口径下旧设备最后一条
读数区间被新设备同刻读数截断，责任在交接点两侧干净分界。

对每条越限读数区间与各虚拟承运区间求交：

```
segSeconds[s] += intersect([ts_i, ts_{i+1}), [segStart, nextSegStart))
```

同时累计该环节下的越限读数条数与峰值。报警仍开启时，最后一条越限区间延伸到
当前时刻（监控大屏看到的"已持续 N 分钟"）。

级别阈值（可在 `src/config.js` 按业务调整）：

- major：偏离 ≥ 2℃ 或持续 ≥ 20 分钟
- minor：偏离 ≥ 0.5℃ 或持续 ≥ 10 分钟

## 7. 回溯产物

`traceShipment()` 聚合：批次信息、环节链（含每环节读数数与观测极值）、
融合时间线（交接/事件/报警开闭）、报警（含责任拆分与越限读数明细）、
温度统计、达标结论。终端报告 `src/report.js` 只是它的一种渲染，
API 返回的结构化 JSON 可直接给前端或监管报送使用。

## 8. 取舍与边界

- **单机 JSONL**：面向单车/单仓量级与监管留痕场景，顺序追加成本极低；
  上规模时事件可改投 Kafka、投影到关系库，领域层不需要改。
- **无鉴权**：设备接入默认内网信任；生产化时在 `/api/readings` 加网关或设备签名。
- **读数时间以设备 ts 为准**：乱序/迟到读数按 ts 排序处理，但报警生命周期按入库顺序推进；
  晚到的历史读数会进入统计与回溯，不会重开已闭环报警（闭环是当时的事实）。
- **多车厢**：同一载具可有多个 compartment（如 C1/C2），报警与责任按车厢独立。
