# 设计说明

## 1. 为什么是事件溯源 + 哈希链，而不是普通数据库表

追溯系统的输出会被用于**定责和索赔**，证据的可信度等于系统的可信度。

- 普通表支持 UPDATE/DELETE，一次 SQL 维护或一次"善意修正"就能让历史温度曲线改变，
  而且无法证明它改变过。
- 本系统把全部业务事实建模为**不可变事件**（读数、交接、超温开关、数据中断），
  只追加写入 JSONL。第 n 条事件携带 `prevHash`，`hash = sha256(prevHash + canonical(事实))`，
  canonical JSON 对键顺序不敏感。
- 校验是流式逐条重算（`EventStore.verify`），大日志不一次性载入内存。
  三种篡改都能在第一条异常处报出序号与原因：**改内容**→哈希不一致；**删事件**→prevHash
  断链；**插事件/重排**→序号不连续或断链。

读侧状态（批次、读数数组、活动告警）只是事件流的投影：进程启动时从头重放得到，
重启后判定状态机也以"活动超温事件 + 最新读数"重建，不需要额外的检查点协议。

代价：不能原地修改数据。纠错的唯一方式是"追加一条更正事件"——这正是审计场景想要的。

## 2. 超温判定：为什么是"立即预警 + 容忍时长计责"而不是单一阈值

冷链运输中开门装卸、冷机化霜必然造成 3~10 分钟的温度波动，它们是**正常作业**。
两种朴素策略都不成立：

- 越限即告警：驾驶端天天被开门误报轰炸，真告警反而被忽视；发货方也会被误判担责。
- 延迟 N 分钟才告警：真故障（冷机停机）的前 N 分钟被浪费，且系统无法解释这 N 分钟。

判定机因此拆成两个目的不同的状态：

```
normal ──越限──▶ watching（立刻向调度/驾驶端推送预警，开始观察）
                  │
                  ├─ 容忍时长内回带内 ─▶ normal，记为"豁免波动"（可见、不追责）
                  └─ 持续越限超过容忍时长 ─▶ alarming（开超温事件，容忍线之后开始计责）
```

- 温区自带 `toleranceMs`：冷冻 10 分钟、冷藏 15 分钟、医药 2~8°C 仅 5 分钟。
  容忍时长是**豁免**而不是延迟——越限事实与预警都保留在链上。
- 超温窗口的越限起点不是"第一个越限读数的采样时刻"，而是用最后一个带内读数与
  首个越限读数对阈值边界做**线性插值**得到，避免 60 秒采样间隔带来的分钟级误差。
- 等级按最大越限幅度：minor <3°C、major 3~8°C、critical ≥8°C。
- 批次完结时仍未恢复的超温按结束时刻强制收口，并标记 `recovered=false`。

## 3. 责任归因规则

责任段由交接时刻切分：发运交接前是发货方仓储，发运→到货是承运方运输，
到货之后是收货方仓储。交接测温是关键证据，规则按证据强度排序：

1. **PRE_COOL_FAILURE（预冷不合格）**：首次越限不晚于发运，且发运交接温度同方向越限
   → 发货方主责；承运人在越限温度下放行，若超温延续到运输段，承担次要责任。
2. **IN_TRANSIT_FAULT（运输故障）**：到货交接温度同方向越限 → 承运方主责；
   到货后至温度恢复期间若仍在计责（滞留卸货），收货方承担次要责任。
3. **DEST_HANDLING（收货失职）**：异常窗口全部晚于到货时刻（签收合格后升温是典型）
   → 收货方主责。
4. **BY_SEGMENT_SHARE / GAP_BY_SEGMENT_SHARE（兜底）**：交接证据不充分或属于数据中断时，
   按异常窗口与各责任段的时间重叠占比归因。

所有规则都会同时输出：主责环节、责任方（名称/联系方式/车牌）、各段计责时长占比、
**逐条人类可读证据**、以及交接记录缺失时的推断标记（如"运输段起点按最早读数推断"）。
责任结论永远可以被人用原始读数与交接记录复核。

## 4. 数据中断的处理

传感器掉线、盲区、记录仪没电与"真的超温"一样会毁掉一批货，但性质不同。

- 同一传感器相邻读数间隔超过 `SENSOR_GAP_MS`（默认 5 分钟）即产生 `data_gap_detected`
  事件，独立于温度状态机。
- 中断窗口同样走责任段归因（掉线发生在哪一段，就由该段先解释）。
- 温度全程合格但存在中断时，报告结论不是 PASS 而是 **REVIEW 存疑待核**——
  无数据不等于合规。

## 5. 入站门禁：为什么坏数据直接拒收而不是打标记

追溯链一旦写入就不可删除，因此写入必须保守。拒收项：物理量程 [-60,80]°C 外的值
（传感器短路/掉线常见 500/-999）、非数字、时间戳乱序或重复、超前服务器时钟 >60s、
批次/传感器不存在或未绑定。批量上报整批原子拒绝（先全量校验再写入），
保证每个传感器的链上时间戳严格递增——这是中断检测和游程分析成立的前提。

## 6. 模拟器的物理模型

`simulator/model.js` 是简化一阶热平衡：

```
dT = (ambient - T) * 热泄漏系数 + 冷机项(-coolingRate) + 噪声
```

- 冷机带温控器（达到 setpoint 停机、回升 hysteresis 再启动），否则恒定制冷会把温度打穿。
- 开门时切换到高泄漏系数 doorLeak，模拟装卸时的快速温升。
- 冷机故障 = 制冷项归零；预冷不合格 = 初始货温就在带外且制冷速率不足；
  收货失职 = 签收后环境温度阶跃到故障库温。
- 随机数用 mulberry32 种子生成，**同一剧本逐字节复现**，既用于演示也直接作为
  回归测试夹具（见 `test/scenarios.test.js`）。

## 7. 显式不做的事（v1 边界）

- 不做多租户/RBAC 与设备证书：网关用单一 Bearer 令牌，生产部署需替换为 mTLS 或设备密钥。
- 日志是本地 JSONL 而非复制日志：多实例部署需要把 append 落到共享存储或加前置写服务。
- 不做地理围栏：路线以起止点文本表示；GPS 与温控的关联是下一版的事（接口已在批次模型里
  预留 route）。
- 温区判定基于静态阈值，没有引入 MKT（平均动力学温度）等累积指标——对短驳冷链，
  窗口+时长模型与现行 GSP/GSP 附录的监管口径一致且可解释性更强。
